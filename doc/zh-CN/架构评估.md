# CilExec 不可变性、可复现性、可预测性评估

## 什么是不可变系统

不可变系统的定义：**系统状态不是通过修改已有构件产生的，而是通过从确定性的输入重新构建整个构件来产生的。**已存在的构件永远不会被原地修改。

Nix 是典型例子：修改 `/etc/nginx/nginx.conf` 不会原地编辑那个文件——它创建一个新 derivation，生成全新的文件树，然后把符号链接从一个 `/nix/store` 路径切到另一个。

## 什么是可复现系统

可复现系统的定义：**给定完全相同的输入（源码、配置、环境），能在任意时间、任意机器上构建出逐字节相同的产物。**不仅仅是"行为相同"，而是**输出哈希相同**。

Debian Reproducible Builds 是典型例子：同一个 `.deb` 包的 SHA-256 在 CI、开发者机器、用户机器上完全一致。

## 什么是可预测系统

可预测系统的定义：**给定已知的初始状态和输入序列，系统的每一个后续状态都可以在不运行系统的情况下被推演出来。**没有隐式状态、没有环境依赖的副作用、没有非确定性的分支。

纯函数式程序是典型例子：`f(x)` 今天调用、明天调用、在 Docker 里调用、在真机上调用——返回值永远相同。

## 逐项评估

### 一、不可变性

#### 1.1 进程快照的写模型

Cilexec 的 `.proc` 文件写入流程：

```
saveToFile()
  ├── 将 processData 序列化为 JSON
  ├── 写入 .proc.tmp
  └── 原子 rename .proc.tmp → .proc
```

**这是一个接近于不可变的模型。** `.proc` 文件本身不会被原地编辑——每次写操作都产生全新的文件内容，然后原子替换。旧内容在替换瞬间消失，不会出现读半截的情况。

但是进程快照**确实在被原地更新**。同一个 PID 的 `.proc` 文件被反复 overwrite。一个真正不可变的进程系统的做法是：

```
/system/process/1/00001.proc   ← 第 1 步后的状态
/system/process/1/00002.proc   ← 第 2 步后的状态
/system/process/1/00003.proc   ← 第 3 步后的状态
...
```

每次状态转移作为一个新文件，旧快照保留为历史。当前状态由"指向最新快照的指针"决定。这样回滚时可以精确回到任意历史状态。

**结论：原子替换接近不可变，但不是真正的不可变系统——旧状态不可恢复。**

#### 1.2 inbox 消息的模型

inbox 的 `.msg` 文件在被 acknowledge 时删除。消息被消费后消失。一个真正不可变的消息系统的做法是：

```
inbox/1/<gen-hash>/applied.list    ← 已消费消息 ID 列表
inbox/1/<gen-hash>/<msg-hash>.msg  ← 消息本身永远不会被删除
```

当前实现是通过**删除消息文件**来标记已消费，这是可变操作——如果恢复逻辑有 bug，消息不可重建。

**结论：消息消费模型是可变操作，不符合不可变系统的设计。**

#### 1.3 effect ledger

effect 去重依赖于 ledger 文件中被追加的条目。EffectLedger 的 `write.ledger` 确实是在追加新记录而非覆盖，这更接近不可变追加日志的模型。

**结论：EffectLedger 的追加日志模式更接近不可变系统的设计。**

### 二、可复现性

#### 2.1 给定相同的源码，能否构建出相同的 JAR？

**不能。** 原因：

| 阻断因素 | 位置 | 影响 |
|---|---|---|
| `maven-shade-plugin` 无 `outputTimestamp` | `pom.xml` | JAR 内条目顺序依赖文件系统遍历序——不同 OS/FS 产生不同顺序 |
| 无依赖锁文件 | 无 `maven-wrapper.properties`、无 `pom.xml.effective` | 传递依赖版本在构建时由 Maven 解析——不同时间、不同仓库可能不同 |
| `maven.compiler.source=26` | `pom.xml:12-13` | 无公开 JDK 26，不同编译器的字节码细节可能不同 |
| build 脚本含绝对路径 | `build/clean.sh:3` | `/Users/administrator/` 硬编码 |

#### 2.2 给定相同的 JAR 和同等 VFS 初始状态，能否复现系统运行状态？

**不能。** 原因：

| 阻断因素 | 说明 |
|---|---|
| 每个进程的 `ProcessGeneration` 使用 `UUID.randomUUID()` | 不同运行产生不同的 generation |
| 每条 IPC 消息的 `messageId` 使用 `UUID.randomUUID()` | 同上 |
| `System.currentTimeMillis()` 被持久化到 `.proc` 的 `RunningTime`、文件元数据的 `CreationTime`/`LastEditTime`、effect ledger 条目的 `Time`、交换池的 `time` | 不同时间运行产生不同的持久化时间戳 |
| `config/init.json` 保存 `vfsRoot.getAbsolutePath()` | 依赖运行时的 `user.dir`——不同目录产生不同内容 |
| 文件 `Owner` 使用 `System.getProperty("user.name")` 或其他调用上下文 | 不同用户运行结果不同 |

即使相同的 FCL 脚本，相同的初始 VFS，在相同代码的 JAR 下运行两次——两次生成的 `.proc` 文件、`.delivery` 文件、exchange pool 文件在字节级别**完全不同**。

#### 2.3 复现性测试

做一个思维实验：运行两次 `mvn clean test`，然后对 `target/` 下输出做 hash。两次结果能逐字节相同吗？

答案是否。至少：
- 每次 `UUID.randomUUID()` 产生不同的 generation
- `System.currentTimeMillis()` 产生的 `RunningTime` 因测试执行时长不同而不同
- swap pool 的 `time.editTime` 随执行时间变化

**结论：Cilexec 不是一个可复现系统。每次运行产生不同的持久化产物。**

### 三、可预测性

#### 3.1 FCL 语言的确定性

如果不调用非确定性函数（`random`、`getTime`、网络调用），FCL 解释器本身是**几乎确定性的**：
- 算术、字符串操作：纯函数
- 控制流：基于表达式结果，无隐式条件
- 变量赋值：按语句序列线性推进

**但这只是解释器层面的确定性。**

#### 3.2 系统层级的非确定性

即使 FCL 脚本完全确定（无 `random()`、无 `getTime()`、无网络调用），以下因素使得系统行为无法在不运行的情况下推演：

| 来源 | 说明 |
|---|---|
| `ProcessGeneration` UUID | fork 时子进程的 generation 无法预先知道 |
| fork 返回的 PID | 依赖系统当前的空闲 PID——而空闲 PID 又依赖之前进程的退出时序 |
| 调度顺序 | Scheduler 按 PID 数字顺序创建 runner，但虚拟线程的实际执行顺序由 JVM 调度器决定 |
| 多进程并发 | 如果一个 FCL 脚本 fork 出 100 个子进程，它们之间的执行交替顺序不可预测 |
| 锁获取顺序 | 多个进程竞争同一文件锁或 swap pool 锁时，获取顺序不可预测 |
| `wait()` 语义 | `wait()` 消费 "任意一个" 子进程的退出事件——消费者不知道具体是哪一个 |

#### 3.3 恢复的可预测性

effect journal 和 inbox 的设计正是为了给 crash recovery 提供确定性——"如果 JVM 在这个位置崩溃，下一次启动时是否确定性地恢复？"

在这点上 Cilexec **做得相对好**：receipt 的三阶段协议（PREPARED → COMPLETED → ledger）确保了无论在哪一步崩溃，恢复后的状态是确定性的。

但仍有缺口：inbox 的 delivery ledger 写入和 `.msg` 文件写入之间不是原子的——两个步骤之间存在崩溃窗口，这期间的状态不可预测。

**结论：FCL 解释器在纯计算层面是确定性的，但系统的并发调度、PID 分配、UUID 生成使得整体行为不可预测。crash recovery 基本可预测，但个别窗口有间隙。**

## 总结

| 维度 | 当前状态 | 要成为真正的不可变/可复现/可预测系统需要什么 |
|---|---|---|
| **不可变性** | 原子替换接近不可变，但不是。旧状态不可恢复。inbox 消息被原地删除。 | 进程快照改为追加归档而非覆盖；inbox 消息标记消费而非删除 |
| **可复现性** | 不能复现。每次运行产生不同的持久化产物。 | 消除运行时的非确定性源：`UUID.randomUUID()` → 确定性生成；`System.currentTimeMillis()` 从快照排除或用逻辑时钟；构建配置添加 `outputTimestamp` |
| **可预测性** | FCL 纯计算可预测，但调度、PID 分配、进程并发不可预测。 | 单进程执行模式可预测；多进程模式将调度序显式化；PID 分配需要是源码中的显式声明而非运行时动态分配 |

Cilexec 的设计理念——零内存状态、磁盘持久化、启动恢复——朝正确的方向。但它仍然是传统的**可变文件系统 + 原子更新**模式，而非真正的**不可变构件组合**模式。两条路距离尚远。
