## 2 进程生命周期

### 状态机

```
  NEW ──→ READY ──→ RUNNING ──→ READY      (时间片结束)
                           │
                           ├──→ BLOCKED     (wait/waitPid/效果恢复)
                           ├──→ PAUSED      (收到 pause 消息)
                           ├──→ TERMINATED  (正常退出/被 kill)
                           └──→ FAILED      (不可恢复异常)
```

### 状态转换规则

| 转换 | 触发条件 | 含义 |
|---|---|---|
| NEW → READY | init() 完成后 | 进程进入调度队列 |
| READY → RUNNING | step() 开始 | 执行一行指令 |
| RUNNING → READY | step() 完成 | 等待下一次调度 |
| RUNNING → BLOCKED | wait() / waitPid() / EFFECT_RECOVERY | 等待子进程或外部恢复 |
| RUNNING → PAUSED | 收到 ProcessState=PAUSED 消息 | 挂起，恢复前不执行 |
| PAUSED → READY | 收到 ProcessState=READY 消息 | 恢复执行 |
| RUNNING → TERMINATED | 代码执行完毕 / __Terminate 消息 | 进程退出 |
| RUNNING → FAILED | 不可恢复异常 | 进程异常终止 |

### 关键数据字段

每个 `.proc` 文件包含：

```json
{
  "PID": 1,
  "Name": "INIT",
  "Owner": "local",
  "ProcessGeneration": "uuid-v4",
  "EffectiveUser": "local",
  "PathAliases": { "home": "/user/local" },
  "ProcessState": "RUNNING",
  "BlockReason": null,
  "ExitReason": null,
  "StateMessage": null,
  "RunningTime": 0,
  "Priority": 0,
  "Parent": { "PID": 0, "Generation": null },
  "Child": {
    "5": { "PID": 5, "Name": "test-5", "Generation": "uuid" }
  },
  "ExitedChildren": { "5": { "PID": 5, "Generation": "uuid", "ExitReason": "NONE" } },
  "ReapedChildren": { "5@uuid": true },
  "Execution": { "SchemaVersion": 1, "NextAttemptOrdinal": 3 },
  "InboxState": { "AppliedMessageIds": { "msg-id-1": 1, "msg-id-2": 2 } },
```

## 3 ProcessGeneration — 代次身份

**核心原则：PID 不是稳定身份。** PID 会被复用（进程退出后，fork 可能分配同一个数字）。`ProcessGeneration` 是每个进程实例的不可变 UUID，作为所有跨进程操作的授权来源。

### 生成时机

- `ProcessIdentity.ensureDefaults()` — 快照缺少 generation 时自动分配新 UUID
- fork 时子进程从预留快照继承 generation
- exec 保留当前 generation

### 生效范围

| 操作 | generation 检查方式 |
|---|---|
| recordChildExit | parentGeneration 和 childGeneration 都不为 null 才执行 |
| reparentToInit | childGeneration 为 null 则拒绝 reparent |
| postMessageToGeneration | 磁盘快照的 ProcessGeneration 必须匹配 |
| kill / pause / continue | 消息的目标 generation 必须匹配快照 |
| 文件锁 | lock 归属 generation，旧 generation 的锁无效 |
| swap pool lock | lease 绑定 generation |
| 进程文件删除 | removeProcessFile 验证 expectedGeneration |
| Scheduler 替换 runner | generation 不匹配则停掉旧 runner |

### 旧快照迁移

`RecoveryManager` 启动时处理没有 generation 的旧快照：
- 自动生成新 generation
- 父子关系：只有当双方快照都明确列出对方时，才补上 generation 并保留关系
- 无法验证的关系（例如父进程 Child 列表有该 PID 但子进程的 Parent 节点不指向该父进程）会被移除

## 4 ProcessRunner — 执行引擎

### 构造与初始化

```
new ProcessRunner(pid, processData)
  ├── ProcessIdentity.ensureDefaults() — 补全 generation、EffectiveUser、PathAliases
  ├── 创建组件：
  │   ├── StateManager     — .proc 持久化 + 代次校验
  │   ├── CodeLoader       — 注释剔除、花括号分割、边界表
  │   ├── ExpressionEvaluator — 词法→语法→求值
  │   ├── ControlFlow      — if/while/break/return
  │   ├── IpcHandler       — fork/exec/kill/wait/pause/continue
  │   ├── FunctionManager  — 用户函数定义与调用栈
  │   ├── ImportManager    — import/include
  │   └── StatementAttemptManager — 指令 try/prepared/complete
  │
  └── init()
      ├── loadRuntimeState() — 从 processData 加载代码、变量、行号、blockStack
      ├── RUNNERS.put(pid, this) — 注册为唯一 runner
      ├── 解析用户函数 (CodeLoader 预扫描)
      ├── NEW/RUNNING → READY (上电即恢复)
      └── persistState()
```

### step() — 核心执行循环

虚拟线程中每次调用 `step()` 只执行 **一行** 代码，执行前后都持久化。

```
step()
  ├── processPendingMessages()          # 处理外部消息
  ├── 检查 running 标志
  ├── executeLine()
  │   ├── 检查是否执行完毕 → 终止或返回调用栈
  │   ├── 跳过空行和注释
  │   ├── 花括号处理 → controlFlow
  │   └── dispatchStatement()
  │       ├── if / while → 条件判断 + 跳转
  │       ├── func → 函数定义注册
  │       ├── import/include → 代码加载
  │       ├── return / break → 退出当前块
  │       ├── exec("path") → 替换代码（保留 PID 和 generation）
  │       ├── 索引赋值 arr[0]=expr
  │       ├── 普通赋值 x=expr
  │       │   ├── 涉及进程间操作的赋值（fork/wait/kill）→ attemptManager.invoke()
  │       │   └── 普通表达式 → expressionEvaluator.evaluateExpression()
  │       └── 通用表达式（函数调用、字面量）
  │           ├── FORK → invokeEngineEffect
  │           ├── KILL/W — S — T/P — WAIT/PID → ipcHandler
  │           └── EXEC → 替换代码
  │
  └── persistState()                    # 持久化到 .proc
```

### 虚拟线程主循环

```
virtualThreadRun()
  while running && !killed && !state.isTerminal():
    step()
    if PAUSED || BLOCKED: parkNanos()
```

### 行号推进策略

- `settle(nextLine)` → 设置 currentLine 并 persistState()
- 进入用户函数体后 `enteredUserFunction=true`，行号在函数体内自主推进
- `controlTransferred=true` 时不推进（exec 已替换代码）

## 5 Scheduler — 调度器

### 职责

1. **进程发现** — 扫描 `/system/process/` 目录，为新 `.proc` 文件创建 ProcessRunner
2. **启动虚拟线程** — 每个进程运行在独立的虚拟线程中
3. **PID 复用处理** — 旧进程退出后相同 PID 出现新 generation
4. **终态清理** — 对终态文件调用 reconcileLifecycle

### 扫描逻辑

```
scanProcessFiles()
  遍历 /system/process/{pid}.proc
  跳过 INIT (PID 1)
  跳过 RUNNERS 中已注册的同一 generation
  终态文件 → 如果有 cleanup 标记，调用 reconcileLifecycle
  已有相同 PID 但 generation 不同 → 停掉旧 runner，创建新 runner
  新发现 → new ProcessRunner(pid, data) → addProcess(runner)
```

### 故障容忍

- 文件连续缺失计数 — 容忍 writeAtomic 原子重命名期间的瞬时读取失败
- 损坏快照保留不变，调度器拒绝创建 runner
- `.proc.tmp` 作为恢复备选，存在时的优先提升

## 6 StatementAttempt — 指令执行尝试

### 设计目标

确保每条 FCL 语句的执行 attempt 在崩溃后可重放，避免重复执行外部副作用。

### 三阶段协议

```
PREPARED  — 尝试已记录（effect ordinal 已分配，但尚未执行）
   ↓
COMPLETED — 副作用已确认完成（receipt 已提交）
   ↓
IN_DOUBT  — 执行过程中崩溃 / 外部效果不确定
```

### 数据结构（在 .proc 的 Execution 字段中）

```json
{
  "Execution": {
    "NextAttemptOrdinal": 3,
    "ActiveAttempt": {
      "Ordinal": 2,
      "Statement": "x = network.fetch(\"https://api.example\")",
      "LineNumber": 5,
      "Effects": [
        {
          "Id": "stmt-2-effect-0",
          "Operation": "network.fetch",
          "Policy": "MANUAL_RECOVERY",
          "Status": "IN_DOUBT",
          "Timestamp": 1234567890,
          "ArgumentSummary": "https://api.example",
          "Result": null
        }
      ]
    },
    "AttemptLedger": {
      "stmt-1": "COMPLETED",
      "stmt-2": null
    }
  }
}
```

### StatementAttemptManager 工作流

```
begin(ordinal, statement)
  ├── 创建 ActiveAttempt
  ├── 写入 ordinal、statement、Effects=[ ]
  └── persistState()

invoke(operation, policy, arguments, invocation)
  ├── 检查先前的 receipt → 如果已 COMPLETED，直接返回保存的 result（重放）
  ├── 检查是否 IN_DOUBT → 抛出 EffectRecoveryRequiredException（阻塞）
  ├── Policy 控制：
  │   ├── PURE → 直接执行（无副作用记录）
  │   ├── RECORDED → 记录 effect → 执行 → 标记 COMPLETED
  │   ├── LOCAL_TRANSACTIONAL → 同上，但 effect ID 写入目标资源
  │   └── MANUAL_RECOVERY → 记录 effect → 执行
  │        ├── 成功 → 标记 COMPLETED
  │        ├── UnknownEffectOutcomeException → 标记 IN_DOUBT → 阻塞
  │        └── 其他异常 → 重试或抛出
  └── persistState()

commit()
  ├── 将 ActiveAttempt 的所有 COMPLETED effect 写入 AttemptLedger
  ├── 清除 ActiveAttempt
  └── persistState()
```

### 崩溃恢复语义

| 崩溃时机 | 恢复行为 |
|---|---|
| PREPARED 写入后、执行前崩溃 | 重新执行（PREPARED 只是 begin 标记） |
| COMPLETED receipt 提交后崩溃 | 后续 step() 读取 receipt，返回保存的 result（**不重复执行**） |
| IN_DOUBT 标记后崩溃 | 后续 step() 抛出 EffectRecoveryRequiredException，进程阻塞 |
| commit() 写入前崩溃 | ActiveAttempt 仍在，重新评估其 Effects 列表 |

### 效果恢复 API

```
system.resolveEffect(pid, effectId, decision, result)
  decision = "retry" | "confirm" | "reject"

  retry   — 将 effect Status 重置为 PREPARED，下次尝试重新执行
  confirm — 将 effect Status 设置为 COMPLETED，result 用作返回值
  reject  — 将 effect Status 设置为 COMPLETED，以 result 为返回值继续执行
```

## 7 EffectPolicy — 副作用分类

### 四种策略

```java
public enum EffectPolicy {
    PURE,              // 无副作用，不记录 receipt
    RECORDED,          // 纯内部副作用，按 receipt 重放
    LOCAL_TRANSACTIONAL,// 内部事务型副作用，effect ID 写入目标资源
    MANUAL_RECOVERY    // 外部未知副作用，需要人工恢复
}
```

### 118 个内置函数的分类（BuiltinFunctionCatalog）

| 策略 | 典型函数 |
|---|---|
| **PURE** | `math.*`、`util.typeOf`、`util.toJson`、`util.fromJson`、`path.*`、`io.print`、`io.println` |
| **RECORDED** | `io.readFile`、`io.writeFile`、`io.input` |
| **LOCAL_TRANSACTIONAL** | `file.*`、`process.fork`、`process.exec`、`process.kill`、`process.pause`、`process.continue`、`user.*`、`swapPool.*` |
| **MANUAL_RECOVERY** | `network.*`、`socket.*` |

### PURE 和 RECORDED 的边界

- `io.print` / `io.println` 是 **PURE** — 控制台输出被视为不可逆但不可判定，不记录 receipt
- `io.writeFile` 是 **RECORDED** — 文件写入是可逆的内部副作用，receipt 用于 crash 后去重
- `network.fetch` / `network.httpPost` 是 **MANUAL_RECOVERY** — 外部 HTTP 调用结果不确定

### MANUAL_RECOVERY 触发条件

- HTTP POST：发送后未收到响应即崩溃
- Socket 写入：操作后无法确认对端是否收到
- 特权外部操作（`system.*`）

`NetworkUtil` 在 POST 请求中携带 `Idempotency-Key: <effectId>` 头，但仍无法确认服务端是否已处理，因此保守地标记为 IN_DOUBT。

## 8 ProcessInbox — 持久化消息收件箱

### 设计目的

进程控制消息（kill、pause、continue）必须**幂等地**抵达正确的进程实例，即使在目标进程不在线、JVM 崩溃、PID 复用的情况下。

### 架构

```
/system/process/inbox/
  ├── deliveries/                    ← 全局 delivery 账本
  │   ├── <sha256(msgId)>.delivery   ← 每一条消息的持久化投放记录
  │   └── <sha256(msgId)>.lock       ← 每条消息的发布锁
  └── <pid>/                         ← 每个 PID 的子目录
      └── <sha256(generation)>/      ← 按 generation 分层
          ├── sequence               ← 单调递增序列号
          └── <sha256(msgId)>.msg    ← 消息文件
```

### 消息结构

```java
record ProcessMessage(
    int schemaVersion,      // 固定 1
    String messageId,       // 全局唯一 ID
    long sequence,          // 跨 messageId 全局递增，用于排序
    int targetPid,          // 目标 PID
    String targetGeneration,// 目标 generation
    int senderPid,          // 发送方 PID
    String senderGeneration,// 发送方 generation
    String field,           // 要更新的字段路径（如 "ProcessState"）
    Object value,           // 字段值
    long publishTime        // 发布时的时间戳
)
```

### 发布流程

```
ProcessInbox.publish(targetPid, targetGeneration, messageId, ...)
  │
  ├── 1. 检查 delivery ledger 是否存在同名记录
  │      ├── 存在且字段/值匹配 → 复用已有消息
  │      └── 存在但不匹配 → 抛出 Message ID collision 异常
  │
  ├── 2. 创建新消息（分配 sequence）
  ├── 3. 写入 delivery 账本（原子重命名 .tmp → .delivery）
  └── 4. ensurePublished()
         ├── 检查 inbox 目录中是否已有 .msg 文件
         └── 没有 → 创建 .msg 文件（原子重命名）
```

### 幂等性保证

```
发送方调用 postMessageToGeneration()
  ├── 1. processData 上检查 AppliedMessageIds → 已应用，返回 true
  ├── 2. delivery ledger 中检查 → 已发布，复用（字段值必须匹配）
  └── 3. 首次发布（上述流程）

应用方 processPendingMessages()
  ├── 遍历 inbox 目录中的 .msg 文件
  ├── 检查 AppliedMessageIds → 已应用的跳过
  ├── 应用字段更新 → 写入 AppliedMessageIds
  └── 删除 .msg 文件（acknowledge）
```

### delivery 账本的作用

`<sha256(msgId)>.delivery` 文件的存在意味着"这条消息 ID 已永久绑定到某个 (targetPid, targetGeneration) 组合"。即使：

- 目标进程已退出 → 不会重新投递到复用相同 PID 的新进程
- JVM 在 .msg 文件创建前崩溃 → 启动恢复会补发

### 启动恢复中的补发

`ProcessInbox.recoverDeliveries()` 扫描 `deliveries/` 目录下的所有 `.delivery` 文件，对每个文件调用 `ensurePublished()` — 若目标 inbox 缺少对应 `.msg` 文件，就重新创建它。

## 9 IpcHandler — 进程间操作

### 操作列表

| 操作 | 实现方法 | effect 记录 |
|---|---|---|
| fork() | handleFork(effectId) | LOCAL_TRANSACTIONAL |
| exec(path) | handleExec(path) | LOCAL_TRANSACTIONAL |
| kill(pid) | handleKill(target, effectId) | LOCAL_TRANSACTIONAL |
| wait() | handleWait() | 不记录（纯阻塞） |
| waitPid(pid) | handleWaitPid(pid) | 不记录 |
| pause(pid) | handlePause(target, effectId) | LOCAL_TRANSACTIONAL |
| continue(pid) | handleContinue(target, effectId) | LOCAL_TRANSACTIONAL |

### fork 流程（详细）

```
handleFork(effectId)
  │
  ├── 1. 检查 ForkLedger
  │      ├── 存在且 parent 不匹配 → 抛出异常
  │      ├── 存在且 CREATED → 检查子进程 .proc
  │      │   ├── 存在且 effectId + generation 匹配 → 恢复父子关系
  │      │   ├── 存在但不匹配 → UnknownEffectOutcomeException（PID 已被其他进程占用）
  │      │   └── 不存在 → 记录为 missing fork result
  │      └── 不存在 → 继续
  │
  ├── 2. 扫描磁盘上 CreatedByEffectId==effectId 的子进程
  │      └── 找到 → 恢复父子关系，markCreated
  │
  ├── 3. 创建新子进程
  │      ├── 分配 PID（原子文件创建 CREATE_NEW）
  │      ├── ForkLedger.reserve() — 记录预留
  │      ├── 从父进程 processData 复制
  │      ├── 清除子进程不应继承的字段（InboxState, LifecycleCleanup, ExitedChildren）
  │      ├── 设置 Parent.Generation = 父进程 generation
  │      ├── 设置 CreatedByEffectId = effectId
  │      ├── 写入 .proc 文件
  │      └── ForkLedger.markCreated()
  │
  └── 4. 更新父进程 Child 列表（包含 Generation 字段）
```

### kill 流程

```
handleKill(target, effectId)
  │
  ├── 1. 检查目标快照的 generation → 不匹配则拒绝
  ├── 2. postMessageToGeneration() — 发送 __Terminate 消息
  │      ├── 目标在线 → unpark 虚拟线程
  │      ├── 目标离线 → 直接写 .proc（状态设为 TERMINATED）
  │      └── 写入 LifecycleCleanup 标记（含 RequestId）
  └── 3. 返回成功

reconcileLifecycle(targetPid, targetGeneration)
  │
  ├── 检查进程是否已 TERMINATED
  ├── 孤儿收养 → reparentSnapshotChildren()
  ├── 通知父进程 → recordChildExit()
  └── removeProcessFile() → 删除 .proc + inbox 目录
```

### wait / waitPid

- 扫描 ExitedChildren（或 ExitedChildren[特定PID]）
- 找到 → 消费退出事件（移到 ReapedChildren），不阻塞
- 没找到 → 设置 BlockReason=WAIT_CHILD，虚拟线程 park

## 10 ForkLedger — Fork 持久化账本

### 目的

fork 的 effect ID 可能被重放，一个父进程的 fork 调用创建的子进程必须被精确恢复。ForkLedger 记录：
- 哪个父 process 调用了 fork
- 分配给哪个子 PID
- 子 process 的 generation

### 数据结构

```
/system/fork/<hash(effectId)>.ledger
```

```json
{
  "EffectId": "stmt-3-effect-0",
  "ParentPid": 42,
  "ParentGeneration": "parent-uuid",
  "ChildPid": 99,
  "ChildGeneration": "child-uuid",
  "State": "RESERVED" | "CREATED"
}
```

### 两阶段提交

```
RESERVED — PID 已分配，子进程预留快照已写入
    ↓
CREATED  — 子进程已创建并写入完成
```

### Crash 恢复

- `RESERVED` 状态 → 检查预留快照是否存在，存在则恢复正常 fork 流程
- `CREATED` 状态 → 检查子进程快照，验证 generation，恢复父子关系
- 预留快照被 `RecoveryManager` 检查：若预留者仍在且活跃 → 保留；若预留者已退出 → 删除预留

## 11 RecoveryManager — 启动恢复

### 调用时机

`Main.main()` → 在启动 Scheduler 线程之前调用 `RecoveryManager.recoverAll()`

### 恢复步骤

```
recoverAll()
  │
  ├── 1. ProcessInbox.recoverDeliveries()
  │      扫描 deliveries/ 下的所有 .delivery 文件
  │      对每条记录 ensurePublished()，补发缺失的 .msg
  │
  ├── 2. 扫描 /system/process/
  │      收集所有 PID（包括 .proc.tmp）
  │
  ├── 3. 对每个 PID：
  │      │
  │      ├── FileUtil.exists() — 自动提升 .proc.tmp 到 .proc
  │      │
  │      ├── Reservation 快照 → 检查预留者是否仍活跃
  │      │   ├── 不活跃 → 删除
  │      │   └── 活跃 → 保留
  │      │
  │      ├── ensureDefaults() — 补充 generation/EffectiveUser/PathAliases
  │      │
  │      ├── reconcileRelationshipGenerations() — 修复旧快照的父子关系
  │      │   ├── Parent.Generation 缺失 → 读父快照验证
  │      │   │   ├── 父快照明确列出该子 PID → 补 generation
  │      │   │   └── 无法验证 → 移除 Parent 身份
  │      │   └── Child.{pid}.Generation 缺失 → 读子快照验证
  │      │       ├── 子快照的 Parent.PID 指向当前 PID → 补 generation
  │      │       └── 无法验证 → 移除该 Child 条目
  │      │
  │      ├── 终态文件 + LifecycleCleanup/TerminationCleanup 标记
  │      │   → reconcileLifecycle() — 完成孤儿收养 + 通知父进程 + 删除文件
  │      │
  │      └── 非终态文件 → recoverInbox() — 应用离线 inbox 中的消息
```

### 关系修复详解 (reconcileRelationshipGenerations)

一个无 generation 的旧快照中：

```
Parent: { "PID": 5 }
Child: { "7": { "PID": 7 } }
```

恢复时：

1. **Parent 修复**
   - 读 PID 5 的快照 → 检查其 `Child` 中是否有当前 PID
   - 有 → 补上 `Parent.Generation: <PID 5 的 generation>`
   - 没有 → 移除 `Parent.PID` 和 `Parent.Name`

2. **Child 修复**
   - 读 PID 7 的快照 → 检查其 `Parent.PID` 是否等于当前 PID
   - 是 → 补上 `Child["7"].Generation: <PID 7 的 generation>`
   - 否 → 从 Child 列表中移除该条目

## 12 LifecycleCleanup — 终态清理

### 目标

进程终止后，需要：
1. 将其活跃子进程收养给 INIT
2. 通知父进程
3. 删除 .proc 文件和 inbox 目录

### 生命周期清理记录

```json
{
  "LifecycleCleanup": {
    "Tombstone": true,
    "Time": 1234567890,
    "ExitReason": "KILLED",
    "RequestId": "kill-message-id",
    "ByGeneration": "generation-uuid"
  }
}
```

### invoke 路径

```
1. 自然退出 (executeLine 检测 currentLine >= codeLines.size())
   → terminateNormally() → prepareLifecycleCleanup(false)

2. 异常退出 (handleException → UnrecoverableException)
   → processData["LifecycleCleanup"] = lifecycleCleanupRecord(data, false)

3. kill 消息 (postMessageToGeneration → applyFieldUpdate → "__Terminate")
   → 在 applyOfflineStateRequest 中写入 LifecycleCleanup(termination=true)

4. 效果恢复拒绝
   → 调用方决定 → terminateProcess → LifecycleCleanup

以上任一触发后，调用 reconcileLifecycle(pid, generation):
   ├── 获取 cleanup gate（per-pid, per-generation 的并发控制）
   ├── 检查快照的 ProcessGeneration → 不匹配则放弃
   ├── 检查 LifecycleCleanup 或 TerminationCleanup 标记
   ├── reparentSnapshotChildren() — 孤儿收养
   ├── finalizeTerminalSnapshot() — notifyParent + recordChildExit
   ├── removeProcessFile() — 删除 .proc
   └── ProcessInbox.removeIncarnation() — 清理 inbox 目录
```

### 并发安全

- `LIFECYCLE_CLEANUP_GATES` — per-(PID, generation) 的 `synchronized` gate
- cleanup 流程中反复验证 generation，防止 PID 复用时误伤新进程
- `removeProcessFile` 在文件锁内验证 expectedGeneration

## 13 FileUtil / EffectLedger — 文件系统与副作用去重

### VFS 元数据格式

```
#<META>
{"Owner":"alice","Permission":{"Owner":"read, write","Others":"read"},"CreationTime":123}
<META>#
实际的用户文件内容...
```

### 文件副作用去重 (EffectLedger)

写入类操作（write、append、create）在 `FileUtil` 中记录 effect receipt：

```
/system/effects/<sha256(path)>/write.ledger
```

ledger 记录：
```json
{
  "<effectId>": {
    "Type": "write",
    "Time": 1234567890,
    "ArgumentHash": "sha256-of-content"
  }
}
```

当一条 write 指令的 attempt 被重放时：
1. EffectLedger 中查找 `effectId`
2. 找到 → 对比 ArgumentHash
   - 相同 → 跳过写入，直接返回
   - 不同 → 冲突检测（意味着同一条指令两次产生不同写入内容 — 数据竞争）

### 资源删除后的保护

```json
// 文件被创建后删除，再创建
// EffectLedger 保存被删除时的 tombstone
{
  "<effectId>": {
    "Type": "delete",
    "Time": 1234567890,
    "Tombstone": true
  }
}
```

之后旧 effectId 重放写入时，检测到 tombstone → 拒绝（文件已被删除重建，不会去修改新创建的同名文件）。

### 文件锁 v2（generation + lease + fencing token）

```
lock(path, pid, generation)
  ├── .lock 文件持有者信息：
  │   { "PID": 1, "Generation": "uuid", "LeaseExpiry": 1234567890, "FencingToken": 42 }
  ├── 续租：持有锁的进程定期更新 LeaseExpiry
  ├── 过期接管：其他进程检测 LeaseExpiry < now → 接管锁（递增 FencingToken）
  └── 写入验证：write/append 时，检查当前 FencingToken，token 不匹配则拒绝
```

**FencingToken** 防止过期锁的旧持有者继续操作。

### 安全约束

- 路径穿越拒绝：文件名和 pool 名不能包含 `..` 或 `/`
- generation 路径使用 SHA-256 hash，不拼接原始 generation UUID
- `io.writeFile` 创建前检查父目录权限
- 非 local 用户不能创建 `/system/process/*.proc`
- Scheduler 拒绝非 system owner 的进程快照
- `users.json` 的 Others 权限清空（防止密码泄露）

## 14 SwapPool — 原子事务 IPC

### 架构

```
/system/swap/<poolName>/<slotName>/<sha256(generation)>/
```

每对有 (pool, slot) 的访问都有一个 `SwapTransaction` 原子上下文。

### 操作模型

| 操作 | 事务性 |
|---|---|
| create(pool, slot) | 原子文件创建 |
| write(pool, slot, data) | 读当前值 + 写新值 = 原子事务 |
| read(pool, slot) | 原子读取 |
| delete(pool, slot) | 原子删除 + 权限检查（仅创建者） |
| waitFor(pool, slot, timeout) | 等待值变化（虚拟线程 park） |
| signal(pool, slot) | 唤醒等待者 |
| sync(pool, slot) | 消费者模式 — 等待新值并消费 |
| times(pool, slot) | 返回当前值的版本号 |

### effect 去重

每个 swap 写操作记录 `AppliedEffects`：
```json
{
  "AppliedEffects": {
    "<effectId>": { "version": 5, "Time": 123 }
  }
}
```

重放时检测 effectId 已存在 → 跳过。

### lock / fencing

- Swap pool lock 基于 generation + lease + fencing token
- `sync/times` 消费去重 — 同一 effectId 不能消费两次

### 安全

- pool 名称和 slot 名称分别校验格式
- 删除操作检查所有权
- 列表访问过滤

## 15 用户与权限系统

### 用户模型

- `users.json` 存储用户凭据（密码哈希）
- `EffectiveUser` 持久化在 .proc 中 — 进程可在自己快照中切换用户
- fork 继承父进程的 EffectiveUser
- exec 保留 EffectiveUser

### 用户事务

```
createUser(username, password)
  ├── 1. 检查 effect receipt — 已创建则幂等返回
  ├── 2. 创建主目录 /user/<username>/
  ├── 3. 写入 users.json
  └── 4. 按收敛顺序提交（先主目录后配置文件）

removeUser(username)
  ├── 1. 检查 effect receipt
  ├── 2. 删除 users.json 中的条目
  ├── 3. 删除主目录
  └── 4. 按收敛顺序提交（先配置文件后主目录）
```

### 权限模型

- **Owner** — 创建者，有读 + 写
- **Others** — 其他用户，默认只读
- **local** — 超级用户，绕过所有权限检查

### ThreadLocal 用户上下文

- `UserUtil.setCurrentUser(name)` — 设置当前线程的身份
- `UserUtil.clearCurrentUser()` — 清除
- ProcessRunner 在 step() 开头设置、结束时清除

## 16 PathAliases — 路径别名

### 两级别名

| 级别 | 存储位置 | 生命周期 |
|---|---|---|
| 全局别名 | `/system/config/aliases.json` | 系统级，永久 |
| 进程别名 | `.proc` 的 `PathAliases` 字段 | 同进程实例 |

### 优先级

进程别名 **覆盖** 全局别名。解析路径时先查进程别名，未命中再查全局。

### 继承规则

- fork → 子进程复制父进程的 PathAliases
- exec → 保留 PathAliases（新代码可能需要同样的工作目录）
- 启动恢复 → 从磁盘快照恢复

### 动态解析

`$HOME` 根据 `EffectiveUser` 动态解析为 `/user/<username>/`。

```
resolve("@work/project") 
  → 查 PathAliases["work"] = "/user/bob/app"
  → 返回 "/user/bob/app/project"
```

## 18 从启动到退出的完整流程

### 启动序列

```
Main.main()
  │
  ├── FileInit.init() — 创建 VFS 目录树、users.json、env.json、INIT.fcl
  │
  ├── 注册 11 个 FunctionProvider
  │
  ├── FileLock 获取 OS 级 VFS 文件锁（防止多实例）
  │
  ├── RecoveryManager.recoverAll()
  │   ├── ProcessInbox.recoverDeliveries()
  │   ├── 扫描所有 .proc / .proc.tmp
  │   ├── generation 迁移 + 父子关系修复
  │   ├── 终态清理
  │   └── 离线 inbox 应用
  │
  ├── ProcessInit.createInitProcess() — 创建 PID 1 .proc
  │
  ├── Scheduler scheduler = new Scheduler()
  ├── scheduler.start() — 启动扫描线程
  │
  ├── ProcessRunner initRunner = new ProcessRunner(1, data)
  ├── initRunner.init() — 注册到 RUNNERS
  ├── scheduler.addProcess(initRunner) — 启动虚拟线程
  │
  └── scheduler.join() — 等待进程树全部退出
```

### 进程创建 & 销毁（含 PID 复用）

```
初始状态：PID 1 (INIT) 在运行

1. PID 1 fork → 创建 PID 2 (generation=A)
2. PID 2 fork → 创建 PID 3 (generation=B)
3. PID 3 正常退出
   → StateManager.cleanup() → notifyParent(PID 2) → removeProcessFile(3)
   → PID 3 .proc 删除 → 有 LifecycleCleanup 的终态标记
4. PID 2 再次 fork → 分配 PID 3 (generation=C)
   → 此时 PID 3 的旧 generation=B 不在系统中
   → 新 generation=C 不受旧影响
   → inbox PID 3/generation=C 是新的独立目录
   → delivery ledger 中绑定到 generation=B 的消息不会被误投

5. 若其间 JVM 崩溃：
   → 残留 inbox 文件属于 generation=B
   → PID 3 被重新分配后 generation=C
   → recovery 不会将旧消息投递到新实例
```

### 单个进程的完整生命周期

```
1. Scheduler 扫描 → .proc 文件存在
2. new ProcessRunner(pid, data)
3. runner.init()
   ├── 加载代码、变量、行号
   ├── 注册到 RUNNERS
   └── 状态 NEW → READY

4. Scheduler.addProcess(runner) → 启动虚拟线程

5. 虚拟线程 loop:
   ├── step()
   │   ├── processPendingMessages()
   │   │   ├── 扫描 inbox/<pid>/<generation>/*.msg
   │   │   ├── 处理 pause/continue/__Terminate 消息
   │   │   └── 应用其他字段更新
   │   │
   │   ├── executeLine()
   │   │   └── dispatchStatement()
   │   │       ├── assignment → attemptManager.invoke()
   │   │       │   ├── begin() → 分配 ordinal
   │   │       │   ├── invoke() → 检查 receipt → 执行 → 标记 COMPLETED
   │   │       │   └── commit() → 写入 AttemptLedger
   │   │       ├── fork → IpcHandler.handleFork()
   │   │       │   └── ForkLedger.reserve → CREATE → markCreated
   │   │       ├── exec → 替换代码行、保留 generation
   │   │       └── kill → postMessage → __Terminate
   │   │
   │   └── persistState()
   │       └── StateManager.save()
   │           └── per-PID 文件锁 → 写 JSON → .proc 文件
   │
   ├── 被 pause 消息 → ParkNanos (等待 continue)
   ├── 被 kill 消息 → running = false → TERMINATED
   ├── 代码执行完 → terminateNormally → TERMINATED
   └── 异常 → terminateWithError → FAILED

6. 终止后：
   ├── prepareLifecycleCleanup()
   ├── reconcileLifecycle(pid, generation)
   │   ├── reparentSnapshotChildren() → INIT
   │   ├── recordChildExit → 通知父进程
   │   └── removeProcessFile(pid, generation)
   │       ├── 文件锁 → 验证 generation → 删除 .proc
   │       └── ProcessInbox.removeIncarnation()
   │
   └── RUNNERS.remove(pid)
```

### 持久化时序（零内存状态）

```
执行 x = y + 1 这行代码的磁盘操作序列：
  step()
    ├── [写 .proc] processPendingMessages()
    │   (外来消息写入 InboxState 和 Program 数据)
    │
    ├── [写 .proc] attemptManager.begin()       ← ordinal++
    │   (ActiveAttempt.Ordinal + Statement)
    │
    ├── [写 .proc] attemptManager.invoke()      ← effect receipt
    │   (ActiveAttempt.Effects[0] = COMPLETED/IN_DOUBT)
    │
    ├── 内存: data.put("x", evaluatedValue)
    │
    ├── [写 .proc] attemptManager.commit()      ← ledger 写入
    │   (AttemptLedger["stmt-N"] = "COMPLETED", ActiveAttempt 清除)
    │
    └── [写 .proc] settle(nextLine)             ← runningCodeLine++
       (最终快照：行号+1 + 数据变化 + attempt 收据)
```

每个 `[写 .proc]` 都是一个原子文件操作（临时文件 + 重命名），所以崩溃可能在**任意两步之间**发生。恢复时：
- 读取 `.proc` 获取最后持久化的状态
- 根据 `ActiveAttempt` 中记录的 effect receipt 决定重放或跳过
- 若 `ActiveAttempt` 不在，说明 `commit()` 已完成，新 attempt 从 `NextAttemptOrdinal` 开始

## 附录：线程模型

### 虚拟线程模式（默认，Java 21+）

- 每个进程各自独立虚拟线程 (`Thread.ofVirtual().start()`)
- Scheduler 仅负责进程发现和启动虚拟线程
- 阻塞操作的进程使用 `LockSupport.parkNanos()`
- 写竞争由 per-PID `ReentrantLock` (persistenceLock) 处理
- 进程间唤醒使用 `VIRTUAL_THREADS.get(pid).unpark()`

### 文件并发安全

- `StateManager.save()` — per-PID 文件锁（JSON 级别的 ReentrantLock）
- `ProcessInbox.publish()` — per-message-id OS 文件锁
- `FileUtil.lock()` — per-path OS 文件锁 + generation + lease
- `LIFECYCLE_CLEANUP_GATES` — per-(PID, generation) Java 对象锁

## 附录：异常体系

```
ProcessException (base)
├── RecoverableException
│   ├── 设置 data._warning
│   └── 进程继续执行下一行
├── UnrecoverableException
│   ├── 设置 data._error
│   └── 进程进入 FAILED 状态
├── RetryableEffectException
│   └── 用于 IPC 操作的临时失败（消息发布重试）
├── EffectRecoveryRequiredException
│   ├── 效果处于 IN_DOUBT 状态
│   └── 进程阻塞等待 system.resolveEffect
└── UnknownEffectOutcomeException
    ├── 外部副作用无法确定结果
    └── 在 attempt 中被标记为 IN_DOUBT
```
