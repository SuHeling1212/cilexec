# Cilexec 包管理器 v1

## 1. 最终模型

Cilexec v1 采用：

> 全局内容寻址对象仓库 + 每用户私有安装根 + 每包直接依赖引用表

每个用户拥有独立包集合，状态位于自己的 App 路径：

```text
/user/<user>/app/package/installed.json
/user/<user>/app/data/package/transactions/
/user/<user>/app/data/package/pins.json
```

归档本体是不可变数据。为避免 Alice 与 Bob 安装同一个包时重复保存，已验证的
`.pack` 按 SHA-256 存入只由包管理器访问的全局对象仓库：

```text
/system/app/package/objects/sha256/<前两位>/<完整哈希>.pack
```

这不等于用户共享安装环境。用户可见性只由各自的 `installed.json` 决定：

```text
Alice root -> A.pack -> A.refs -> B.pack
Bob root   -> C.pack -> C.refs -> B.pack
```

Alice 和 Bob 可以拥有完全不同的根包与版本组合；内容相同的 `B.pack` 只占一份空间。

## 2. VFS 结构

```text
/system/app/
├── package/
│   └── objects/
│       └── sha256/<prefix>/<hash>.pack
└── data/
    └── package/
        ├── index.json
        ├── refs/<hash>.json
        ├── repository/
        └── staging/

/user/<user>/app/
├── package/
│   └── installed.json
└── data/
    └── package/
        ├── pins.json
        ├── transactions/<transaction-id>.json
        └── packages/<namespace>/<name>/
```

`package/` 与 `data/package/` 的目录和状态文件归对应用户所有，`Others` 权限为空。
新用户由 `UserUtil.createUser` 创建时会自动获得完整目录结构；系统启动也会修复旧用户
缺失的包目录。

每个包的持久数据使用版本无关目录
`/user/<user>/app/data/package/packages/<namespace>/<name>/`。升级沿用数据，卸载默认保留，
包之间不能共享该目录。

## 3. `.pack` 格式

`.pack` 是严格、确定性的 ZIP v1：

- 所有条目必须使用 `STORED`，不允许压缩。
- 路径按 UTF-8 字典序写入。
- 时间统一为 `1980-01-01 00:00:00`。
- 不写 ZIP comment、可变 extra、目录条目或宿主权限。
- 拒绝绝对路径、反斜杠、空组件、`.`、`..`、隐藏组件和重复条目。
- 拒绝符号链接。
- 最多 4096 个文件。
- 单文件最大 16 MiB。
- 归档和总内容最大 128 MiB。

包身份是最终归档原始字节的哈希：

```text
PackageHash = SHA-256(exact .pack bytes)
integrity   = "sha256:" + PackageHash
```

哈希不写回 `manifest.json`，避免自引用。Cilexec 的文件 Owner、时间、锁和 fencing
元数据也不会进入归档。`package.build` 会先把 VFS 源目录净化到 staging：忽略 `.META`，
只打包文件正文。

## 4. 包目录

```text
manifest.json
payload/**/*.fcl
resources/**
hooks/*.fcl
docs/**
LICENSE
README.md
```

规则如下：

- `manifest.json` 必须位于归档根。
- 普通代码只能放在 `payload/`。
- 生命周期代码只能放在 `hooks/`。
- `.fcl` 不允许出现在其他目录。
- `entry`、export module、resource 和 hook 必须真实存在。
- export 指向的 `func` 必须能在声明模块中找到。
- 所有文本与 FCL 文件必须是合法 UTF-8。

## 5. Manifest v1

```json
{
  "schemaVersion": 1,
  "namespace": "follarce.examples",
  "name": "demo-greeter",
  "version": "1.0.0",
  "entry": "payload/main.fcl",
  "exports": {
    "greet": {
      "module": "payload/main.fcl",
      "symbol": "greet"
    }
  },
  "dependencies": [],
  "lifecycle": {
    "preInstall": {
      "script": "hooks/pre-install.fcl",
      "timeoutMs": 5000
    }
  },
  "resources": ["resources/defaults.json"],
  "license": "MIT"
}
```

包坐标为 `namespace/name@version`。版本必须是精确 SemVer。v1 不接受 `latest`、
`^1.0.0`、`>=1.0.0` 等范围。

依赖格式：

```json
{
  "binding": "unicode",
  "namespace": "follarce",
  "name": "unicode",
  "version": "1.8.0",
  "integrity": "sha256:<64位小写十六进制>"
}
```

安装器同时验证坐标、版本和真实归档哈希。同一坐标如果已经登记了另一个哈希，会以
`Package version pollution` 拒绝，防止发布后替换同版本内容。

## 6. 构建

宿主机 CLI：

```bash
mvn package

java -cp target/cilexec-1.0-SNAPSHOT.jar \
  com.follarce.pack.PackageCli \
  build packageTEST /tmp/demo-greeter-1.0.0.pack

java -cp target/cilexec-1.0-SNAPSHOT.jar \
  com.follarce.pack.PackageCli \
  inspect /tmp/demo-greeter-1.0.0.pack
```

FCL 中从 VFS 源目录构建：

```fcl
result = package.build(
    "/user/alice/app/demo-source",
    "/user/alice/app/demo-1.0.0.pack"
)
```

普通用户的构建源与输出必须位于自己的 `/user/<user>/` 下。`local` 是超级用户。
`package.build` 使用 `MANUAL_RECOVERY`，如果系统在归档发布瞬间崩溃，需要明确决定
是否重试，以免覆盖一个结果未知的输出文件。

## 7. 安装与依赖解析

```fcl
result = package.install("/user/alice/app/demo-1.0.0.pack")
```

可选绑定和本地仓库：

```fcl
result = package.install(
    "/user/alice/app/repository/demo-1.0.0.pack",
    "demo",
    "/user/alice/app/repository"
)
```

缺失依赖按以下顺序寻找：

1. 已存在的全局内容对象。
2. 根 `.pack` 所在目录。
3. 第三个参数指定的本地仓库目录。
4. `/system/app/data/package/repository/`。

解析器递归验证完整依赖图，为每个包生成自己的直接引用表：

```json
{
  "schemaVersion": 1,
  "ownerPackageHash": "sha256:<A>",
  "references": {
    "B": {
      "namespace": "follarce",
      "name": "B",
      "version": "2.0.0",
      "targetPackageHash": "sha256:<B>"
    }
  }
}
```

`A.refs` 只包含 A 的直接依赖。B 的传递依赖由 `B.refs` 解析，不会平铺到 A。

## 8. 安装事务与可见性

主要状态：

```text
PREPARING
RESOLVING
VERIFIED
PRE_HOOKS_COMPLETED
OBJECTS_COMMITTED
COMMITTING_ROOT
ROOT_COMMITTED
POST_HOOKS_FAILED
COMMITTED
ABORTED
```

流程：

```text
验证完整图
-> 执行 pre hooks
-> 提交不可变 objects、refs、index
-> 写入 COMMITTING_ROOT 事务
-> 原子替换用户 installed.json
-> 标记 ROOT_COMMITTED
-> 执行 post hooks
-> COMMITTED
```

用户根文件的原子替换是唯一可见性边界：

- 边界前失败：安装不可见，事务 `ABORTED`。
- 边界后失败：安装保持可见，事务记录待重试 post hook。
- 如果恰好在根替换后、状态更新前崩溃，启动恢复会比较真实用户根，识别已经跨过边界。
- objects 或 index 中的边界前孤儿不会对任何用户可见，之后可由 GC 清理。

相同 binding 安装不同版本时执行原子升级：旧根与新根一次切换，不出现中间空窗。

## 9. 生命周期 hook

顺序：

```text
安装：依赖优先 preInstall -> 根提交 -> 依赖优先 postInstall
卸载：根优先 preUninstall -> 根删除 -> 根优先 postUninstall
```

`preInstall` 或 `preUninstall` 失败、超时、返回 `allow: false` 时中止根变更。
`postInstall` 或 `postUninstall` 失败时不回滚已经提交的根，事务进入
`POST_HOOKS_FAILED`，启动时再次执行尚未完成的 hook。

只读上下文：

```text
__package_event
__package_namespace
__package_name
__package_version
__package_hash
__package_binding
__package_scope
__package_user
__package_data
__effect_id
```

返回值：

```fcl
hookResult = {"status": "ok", "allow": true, "message": "ready"}
```

hook 在有超时和最多 100000 条语句的轻量 FCL 沙箱中执行。允许纯计算、只读操作、
可重试的本地事务操作和普通输出；拒绝 `package`、`process`、`system`、`network`、
`socket`、`user` 操作以及不可安全重试的 effect。hook 不能声明函数、导入代码或修改
上述只读上下文。每个允许的本地 effect 都获得从事务 effectId 派生的稳定 ID。

## 10. 导入

安装后使用：

```fcl
import demo-greeter.*
```

也可显式写当前用户自己的安装根：

```fcl
import /user/alice/app/package/demo-greeter.*
```

同一进程使用多个版本时，为每个安装 binding 指定独立 FCL 命名空间：

```fcl
package.install("/user/alice/app/demo-greeter-1.0.0.pack", "greeter-v1")
package.install("/user/alice/app/demo-greeter-2.0.0.pack", "greeter-v2")

import greeter-v1.* as greeter1
import greeter-v2.* as greeter2

oldMessage = greeter1.greet("FCL")
newMessage = greeter2.greet("FCL")
```

别名必须符合 `[A-Za-z_][A-Za-z0-9_]*`，不能占用已注册的内建 FunctionProvider
命名空间，同一进程中也不能把一个别名重新绑定到另一个包。相同包可以使用不同别名
重复导入；同一包与同一别名的重复导入是幂等的。

解析顺序：

1. 当前有效用户 `installed.json` 中的 binding。
2. 没有已安装 binding 时，回退到现有相对或绝对目录包导入。

加载器直接读取已验证 `.pack`，按每包 refs 递归并以依赖优先顺序加载
`payload/**/*.fcl`。包内的 `import dependency.*` 必须对应 manifest 中声明的 binding；
加载时会验证并去除该行，因为依赖图已经按精确哈希加载。

带别名导入会把根包函数注册为 `别名.函数`，并为该导入实例中的每个依赖哈希建立
不可见的内部命名空间。因此两个版本即使具有相同函数名和不同依赖版本，也可以在
同一个 PID 中正确工作。包内推荐用 `dependency.function()` 明确调用依赖；为兼容旧包，
未限定调用在只有一个直接依赖提供该函数时也会自动绑定，存在歧义则拒绝导入。

不带别名的 `import 包.*` 继续使用原来的扁平函数表，以保持现有脚本兼容。两种模式
都会加载全部 payload 函数；`exports` 用于验证公开入口，但尚不形成严格的运行时隐藏
边界。别名隔离的是函数定义和函数调用，包 payload 应继续以函数定义为主要接口。

进程的 imports 持久化为：

```text
pack:<hash>!/payload/main.fcl
pack:<hash>!/payload/main.fcl#fcl-as=<alias>;root=sha256:<root-hash>
```

运行中进程使用的哈希会成为 GC 根。卸载包不会破坏正在运行或崩溃后待恢复的进程。

## 11. 卸载、pin 与 GC

```fcl
package.remove("demo-greeter")
package.pin("demo-greeter")
package.unpin("demo-greeter")
```

卸载只从当前用户根移除 binding，不立即删除共享对象。GC 从以下根执行 mark-sweep：

- 所有用户的 installed roots。
- 所有用户的 pins。
- 未完成 post hook 事务。
- 活跃持久化进程中的 `pack:<hash>!/...` imports。

全局对象 GC 只允许 `local` 用户执行：

```fcl
report = package.gc()
```

普通用户只能按完整哈希 pin 自己安装图中可达的对象，不能借此访问其他用户的包。

## 12. 查询和资源 API

```fcl
packages = package.list()
detail = package.info("demo-greeter")
report = package.verify("demo-greeter")
defaults = package.resource("demo-greeter", "resources/defaults.json")
```

`verify` 会重新计算每个 `.pack` 的真实 SHA-256，并检查 manifest、全局坐标索引、
直接 refs 和依赖对象。`resource` 只读取 manifest `resources` 中显式声明的 UTF-8 资源。

## 13. EffectPolicy

| API | Policy |
|---|---|
| `package.list/info/verify/resource` | `RECORDED_RESULT` |
| `package.install/remove/gc/pin/unpin/recover` | `LOCAL_TRANSACTIONAL` |
| `package.build` | `MANUAL_RECOVERY` |

安装、卸载事务文件保存调用方稳定 effectId。进程语句崩溃重放时，同一个 effectId 会
读取同一个事务，而不是创建第二次安装。

## 14. 启动恢复

启动顺序：

```text
FileInit
-> 注册 FunctionProvider
-> PackageInit（目录修复与事务恢复）
-> ProcessInit / RecoveryManager
-> Scheduler
```

FunctionProvider 先注册，是为了让待恢复的 post hook 能调用允许的 FCL 内建函数。
未跨过用户根边界的中断事务会标记 `ABORTED`；已经跨过边界的事务会继续未完成的
post hook。`local` 还可以手动触发 `package.recover()`。

## 15. v1 边界

当前版本有意不实现以下内容：

- HTTP/远程仓库。
- 包或仓库数字签名。
- 模糊版本范围与 SAT 求解。
- ZIP 压缩算法。
- 二进制 VFS 资源 API。
- 严格的 export 运行时隐藏。

这些不是安装一致性的缺口。v1 已完成不可变哈希、用户隔离、精确依赖、原子根、
稳定 effect、生命周期恢复、完整性校验和可达性 GC；网络与签名可在这个基础上增加。
