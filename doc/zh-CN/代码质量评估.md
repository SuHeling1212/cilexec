# CilExec 代码质量评估报告

## 一、不可变性

### 评分：中

### 1.1 全局静态可变状态（共 12 处）

| 位置 | 变量 | 类型 | 评分 |
|---|---|---|---|
| `ProcessRunner:53` | `RUNNERS` | `ConcurrentHashMap` | 安全（CAS 操作正确） |
| `ProcessRunner:55` | `LIFECYCLE_CLEANUP_GATES` | `ConcurrentHashMap` | 安全（synchronized gate） |
| `ProcessRunner:96` | `VIRTUAL_THREADS` | `ConcurrentHashMap` | 安全（CAS remove） |
| `Scheduler:24` | `allProcesses` | `ConcurrentHashMap` | 安全 |
| `PathUtil:15` | `vfsRoot` | `File` | **无同步** ⚠️ |
| `PathUtil:16` | `envAliases` | `volatile Map` | 安全（volatile + 不可变快照） |
| `FunctionRegistry:15` | `providers` | `ArrayList` | 可接受（启动时写，之后只读） |
| `FunctionRegistry:16` | `userFunctionsByPid` | `ConcurrentHashMap` | 安全（per-PID 隔离） |
| `SocketUtil:21-23` | `connections`, `serverSockets`, `connIdCounter` | `ConcurrentHashMap` + `AtomicInteger` | 安全 |
| `Main:31` | `scheduler` | `Scheduler` | 可接受（主线程独有） |
| `Logger:17-21` | `writer`, `currentLevel`, ... | 多种 | 安全（synchronized） |
| `ProcessInbox:25` | `LOCAL_GATES` | `ConcurrentHashMap` | 安全但 **内存泄漏** ⚠️ |

### 1.2 核心问题

**`ProcessInbox.LOCAL_GATES` 只增不删（第 25 行）：**
```java
private static final ConcurrentHashMap<Path, ReentrantLock> LOCAL_GATES
    = new ConcurrentHashMap<>();
```
`computeIfAbsent` 持续添加条目，永不清除。长时间运行下导致内存无限增长。如果需要修复：在目录删除时级联移除对应的 gate entry。

**`PathUtil.vfsRoot` 无同步（第 15 行）：**
```java
private static File vfsRoot;
```
`setVfsRoot()` 和读取方之间没有 happens-before 关系。实际上由于在 Scheduler 启动前调用，风险较低，但不规范。

### 1.3 进程级状态

进程快照（`processData` Map）作为可变 Map 在 runner 之间传递。虽然 `persistenceLock` 保护了线程安全，但任何持有引用的代码都可以直接修改 Map。没有不可变包装层（如 `Collections.unmodifiableMap`）来防御意外修改。

### 1.4 总结

整体上共享状态通过 `ConcurrentHashMap` + CAS 保护，设计上偏实用而非严谨不可变架构。进程间的隔离通过 per-PID 数据结构实现，基本安全。但 `LOCAL_GATES` 的内存泄漏和 `vfsRoot` 的同步缺失是两个实际缺陷。

## 二、包管理

### 评分：低

### 2.1 依赖声明

| 依赖 | 版本 | 锁定？ | 用途 |
|---|---|---|---|
| `gson` | 2.10.1 | 是 | JSON |
| `junit-jupiter` | 5.11.4 | 是 | 测试 |

只有 **1 个运行时依赖**（Gson），没有依赖树膨胀的问题。但：

- **无锁文件（lock file）**：没有 `pom.xml.effective`、`maven-wrapper.properties`。传递依赖版本在构建时解析，不能保证不同机器的构建一致性。
- **Java 26**：`pom.xml:12-13` 指定 `maven.compiler.source=26` / `target=26`——这并非公开发布的 JDK 版本。任何不持有此 JDK 的系统都无法构建。
- **版本号不一致**：`package.sh` 和 `package.bat` 引用 `cilexec-1.0.0-ALPHA-3.jar`，但 `pom.xml` 声明 `1.0-SNAPSHOT`。脚本已过时。

### 2.2 构建脚本质量问题

| 文件 | 问题 |
|---|---|
| `build/clean.sh:3` | **硬编码绝对路径** `/Users/administrator/project/Cilexec`，其他机器无法运行 |
| `build/package.sh:9` | Jar 名版本号与 pom.xml 不一致 |
| `build/package.bat:9` | 同上 |
| `build/package.sh:10` | 打包后**自动运行应用**作为副作用 |
| 全部脚本 | **无可复现构建标志**：无 `project.build.outputTimestamp`，无 `-Dreproducible` |

### 2.3 无包管理系统

FCL 脚本的 `import` 仅从 VFS 内部加载文件，不存在类似 npm/pip/cargo 的外部包注册表或依赖解析机制。`include` 是内联复制，没有版本控制。这是教学系统设计的自然结果，但对实际使用是限制。

### 2.4 总结

单依赖的简单性避免了大多数包管理问题，但构建脚本硬编码路径、缺失版本锁文件、JDK 26 要求使得项目在标准环境中难以复现构建。

## 三、报错机制

### 评分：中低

### 3.1 异常被静默吞没（共 19 处）

多处 catch 块只写一行日志后继续执行，或用空块忽略异常。以下是高影响类别：

**（A）RecoveryManager——全部 5 个 catch 块静默丢弃异常**

```java
// RecoveryManager:28
} catch (NumberFormatException ignored) {}

// RecoveryManager:127
} catch (Exception ignored) { return false; }

// RecoveryManager:143
} catch (Exception ignored) { return false; }

// RecoveryManager:158
} catch (Exception ignored) { return null; }

// RecoveryManager:185
} catch (Exception ignored) {}
```

后果：任何损坏的 `.proc` 文件在恢复期间被无声跳过。PID 不会被恢复，但无任何可见提示。

**（B）虚拟线程最外层 catcher——只记日志不设故障状态**

```java
// ProcessRunner:365
} catch (Exception e) {
    Logger.error("Virtual thread for PID " + pid + " crashed: " + e.getMessage());
}
```

后果：进程崩溃时 `.proc` 文件停留在崩溃前的任意中间状态。不会标记 FAILED，不会触发 LifecycleCleanup。该进程在 RUNNERS 中保留脏条目，Scheduler 不知情。

**（C）`Error` / `Throwable` 无保护**

所有 catch 块只捕获 `Exception`，不捕获 `Error`。发生 `OutOfMemoryError` 或 `StackOverflowError` 时，Error 会直接传播到 JVM 的 UncaughtExceptionHandler，进程快照不完整。

**（D）Scheduler 主循环——错误后静默继续**

```java
// Scheduler:116
} catch (Exception e) {
    Logger.error("Scheduler error: " + e.getMessage());
}
```

后果：若调度逻辑内部出现 NPE，会在每个 50ms tick 重复发生，无终止或降级。

### 3.2 ERROR_MARKER 返回模式——调用方无检查

11 个 FunctionProvider 将错误作为 `new String[]{Constants.ERROR_MARKER, ...}` 返回，但这个数组**在 ProcessRunner 中没有集中转换检查**。ProcessRunner 将这个数组作为普通值处理——直接赋给变量或作为表达式参与运算。`FunctionRegistry.isErrorResult()` 方法存在但**从未被调用**——死代码。

```java
// FunctionRegistry:198-207 — 存在但从未被调用的方法
public static boolean isErrorResult(Object result) {
    if (result instanceof Object[]) {
        Object[] arr = (Object[]) result;
        return arr.length > 0 && Constants.ERROR_MARKER.equals(arr[0]);
    }
    return false;
}
```

### 3.3 日志后继续 vs 日志后停止

审计发现 26 处 `Logger.warn` / `Logger.error` 后执行继续（而非停止或抛出）。仅 9 处日志后正确抛出或返回。这意味着多数非关键错误被降级为警告，系统尽可能继续运行——这在教学系统中可以接受，但对可靠性要求高的环境有风险。

### 3.4 总结

报错机制采用"尽可能继续运行"的策略，适合教学演示。但虚拟线程 crash 无声息、ERROR_MARKER 无检查、Error 无保护是三个实际缺陷。不适合对可靠性有严格要求的场景。

## 四、可复显性

### 评分：低

### 4.1 非确定性来源

| 来源 | 位置 | 影响 |
|---|---|---|
| `UUID.randomUUID()` | 7 处（generation、消息 ID、fork/kill 请求） | 每次运行生成不同的 ID |
| `System.currentTimeMillis()` | 30+ 处 | 时间戳被持久化到 .proc 文件、effect ledger、锁租约 |
| `System.getProperty("user.dir")` | `Main:122` | VFS 根目录随工作目录变化 |
| `Math.random()` | `MathFunctionProvider:32` | FCL 脚本可调用，按设计 |
| `FileUtil.getCurrentTimeArray()` | `FileInit` 的 init.json、users.json | 配置文件包含绝对时间戳 |

### 4.2 锁租约依赖系统时钟

文件锁和 swap pool 锁全部以 `System.currentTimeMillis()` 判定租约过期。在慢速或时钟偏移的机器上，锁的行为不可复现。测试中 `Thread.sleep`、`System.nanoTime` 等的使用进一步增加了定时不稳定。

### 4.3 构建不可复现

- 无 `project.build.outputTimestamp`
- 无 Maven wrapper（`mvnw`）
- `maven-shade-plugin` 打包的 uber-JAR 中的条目顺序依靠文件系统遍历顺序（不确定序）
- Java 26 编译目标不可公开获得

### 4.4 测试的确定性问题

部分测试使用 `.nanoTime()` 轮询（如 `ProcessLifecycleEdgeTest:377`），在负载较高的机器上可能超时。`ProcessEffectCrashTest` 通过强制 JVM 终止验证崩溃恢复，但依赖子进程存活时间窗口——这在 CI 中可能不稳定。

### 4.5 总结

进程 generation、时间戳、锁租约全部依赖于不可复现的系统状态。即使代码逻辑完全相同，连续两次运行的持久化产物（.proc 文件内容）在字节层面也不一致。这对调试、审计和 CI 缓存都有影响。

## 综合评估

| 维度 | 评分 | 关键问题 |
|---|---|---|
| **不可变性** | 中 | `LOCAL_GATES` 内存泄漏，`vfsRoot` 无同步，processData Map 无不可变包装 |
| **包管理** | 低 | 无依赖锁文件，JDK 26 不可公开获得，构建脚本版本不匹配含硬编码路径 |
| **报错机制** | 中低 | 19 处静默吞异常，ERROR_MARKER 无检查，虚拟线程 crash 无声息，Error 无保护 |
| **可复显性** | 低 | UUID 随机、时间戳持久化、锁租约依赖时钟、构建时间戳不一致 |

### 优先级排序

1. **高优**：`virtualThreadRun` crash 后应设置 FAILED 状态并触发 LifecycleCleanup
2. **高优**：`FunctionRegistry.isErrorResult()` 应在 ProcessRunner 中调用以在变量赋值前检测错误
3. **中优**：添加 `pom.xml.effective` 或用 `mvnw` + `maven-wrapper.properties` 锁定构建环境
4. **中优**：修正 `build/clean.sh` 中的硬编码路径
5. **低优**：为 `LOCAL_GATES` 添加回收机制
6. **低优**：构建中添加 `project.build.outputTimestamp` 以实现可复现 JAR，同时将时间戳生成延迟到执行时而非构建时

### 合理的设计取舍

以下项在教学系统上下文中是合理的：
- 错误后静默继续（保持系统尽量运行，不崩溃）
- 无外部包注册表（教学系统的使用范围有限）
- UUID 非确定性（每个进程实例本就需要唯一身份）
- 时间戳持久化（审计和调试所需）
