# FCL 可执行产物（V003）

CilExec 0.0.3 引入 V003 可执行程序产物。这次变化的是程序如何持久化和恢复，不改变 FCL
源代码语法；FCL 语言版本统一为 `fcl-0.0.3`。使用 `fcl-0.0.2` 的 V002 包仍可导入。

| 项目 | 版本 |
| --- | --- |
| CilExec 发布版本 | `0.0.3` |
| 数据库迁移 | `V003` |
| 可执行产物格式 | `FCLB` v3 |
| FCL 源语言 | `fcl-0.0.3` |

## 保存的内容

每个新程序都有两个不可变 VFS 对象：

```text
源码对象（.fcl）
  └── 人可以阅读、导出和重新编辑的原始 FCL 源码

可执行对象（.fclb）
  ├── FCLB 魔数
  ├── 可执行格式版本（3）
  ├── 独立源码对象的 SHA-256
  ├── 平铺指令表
  ├── 表达式树
  ├── 函数元数据
  └── 类、字段和方法元数据
```

FCLB 故意不再重复保存源码。VFS 内容哈希保护整个二进制产物；其中保存的源码哈希把它与独立
保留的源码对象绑定。程序数据库行保存这两个对象哈希以及可执行格式版本。

恢复时，Runtime 直接加载 FCLB，不重新解析、不重新编译源码。它会在执行前校验 FCLB 头、格式
版本、内嵌源码哈希、源码对象和程序数据库行的身份是否全部一致。

这个对象图由 CilExec 自己的版本化编码器保存，绝不使用 Java 对象序列化作为持久格式。

## Continuation 与恢复

Continuation 的程序计数器指向创建该程序时的那份不可变 FCLB 指令表。V003 continuation 使用
匹配的版本化 continuation envelope。PostgreSQL 的事务规则不变：一个切片的 continuation 和
所有语义状态要么一起提交，要么全部不提交。

## 从 V002 升级

升级前先创建并验证逻辑备份，然后安装 0.0.3 Runtime，按正常迁移流程执行 `V003`。0.0.3 启动时
只接受数据库 Schema 版本 3。

已存在的 V002 程序不会被原地改写。它们的 JSON 源码容器和 V002 continuation 仍可读取，升级后的
Runtime 可以安全执行完它们。新建程序（包括新的终端提交）一定使用 FCLB v3。若要明确转换某个旧
程序，请用它保留的源码重新提交或重新创建；这会生成新的、不可变的 V003 程序身份和 FCLB 对象。

## 相同源码的再次提交

`include` 展开后，CilExec 会先计算最终源码字节的哈希，再决定是否编译。当前用户若已经拥有相同
源码哈希、语言版本和 FCLB 格式的程序，系统直接返回原有程序并复用其源码与 FCLB，不会再次编译。
并发提交相同源码时，两边仍可能同时开始编译，但数据库唯一约束最终只会保存一个程序身份。

不提供自动降级；回滚方式是恢复升级前备份。

## 程序的显式删除

FCLB 是可恢复执行所需的持久化产物，CilExec 绝不按时间表删除程序。Program 行、源码对象和
FCLB 对象会一直保留，直到管理员显式删除：

```fcl
program.remove(programId)
```

若该 Program 仍被引用，调用会拒绝删除：只要有任何状态的进程使用它，或任何其他 Program 将它
作为模块导入，就返回引用报告（`removed=false`，附阻塞的 PID 和导入方 Program ID）而不删除。
删除成功后，源码与 FCLB 变为不可达对象；由管理员执行的 `storage.purgeUnreferenced([limit])`
回收器会在独立的一小时安全窗口后释放其实际字节。结束进程若不再需要，仍由
`process.removeFinished()` 显式删除其持久化状态。

## 命令行生成产物

```bash
./tools/fcl_compile.sh program.fcl program.fclb
```

这会生成独立的 FCLB 可执行产物，适合检查或工具使用；Runtime 程序本身仍会保留源码对象，并在
加载时校验源码哈希。
